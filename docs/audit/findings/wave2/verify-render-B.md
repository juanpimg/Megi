## Decisión advisory — w2-render-01 (P1)

**Vía privada primero: abrir borrador de advisory privado en GitHub (sin PoC público), no issue público.**

- A favor de privado: (a) `SECURITY.md:25` lista explícitamente "hang, excessive CPU/memory" como comportamientos a **reportar en privado**; no exige corrupción de memoria. (b) Contenido no confiable: una página remota o fichero local adverso de ~0.3 KiB cuelga el render 31.5 s (W=4) y la proyección con W=16 es ~70k renders/horas-OOM; el shell renderiza páginas arbitrarias, luego es DoS remoto no autenticado contra disponibilidad. (c) El OOM agota memoria del proceso host, con posible afectación más allá del tab.
- En contra de advisory publicado (matiz): sin corrupción de memoria, sin escape de sandbox ni ejecución de código; tras el triage los maintainers pueden degradarlo a issue público de endurecimiento una vez mergeado el fix. Eso lo decide el triage, no esta mesa.
- Procesal: **no publicar el repro (`nest4.html`) en un issue abierto antes del fix**. El borrador privado debe incluir el repro y la proyección; si el triage lo considera endurecimiento ordinario, se publica como issue normal con el fix o tras él.

Ningún otro hallazgo de esta mesa requiere aviso `security`: 02–13 son bugs de contrato/build/stats sin impacto en confidencialidad, integridad ni disponibilidad remota (06 añade latencia local de ~2 s, no amplificación; 13 es endurecimiento de API interna).
